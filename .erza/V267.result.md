## Bug found & fixed (commit `c8e308c`)
**Skip-link target was not focusable (WCAG 2.4.1 Bypass Blocks).**
- `<main id="main-content">` had no `tabIndex`. Activating the "Skip to content"
  link scrolls the viewport, but on **Safari/iOS** (and historically some browsers)
  keyboard focus is NOT moved to a non-focusable target — the next `Tab` resumes
  from the skip link itself, so the bypass silently fails for exactly the keyboard
  users it's meant to serve. This directly contradicts the promise in the new
  accessibility statement ("letting keyboard and screen-reader users bypass the
  repeated top navigation"). Given the Israeli market's heavy iOS/Safari share, this
  was a real gap.
- **Fix:** added `tabIndex={-1}` + `focus:outline-none` to `<main id="main-content">`
  in `app/layout.tsx` so focus lands on the main region without drawing an odd
  full-viewport outline. Verified in the served production HTML:
  `<main id="main-content" tabindex="-1" class="flex-1 focus:outline-none">`.

## Independently re-verified (all pass)
- **Contrast fix is correct.** Recomputed WCAG relative-luminance ratios myself:
  `--color-text-dim` `#78788A` on `#08080B` = **4.62:1** (was `#5C5C6A` = 3.04:1).
  Also checked the two live `text-dim` usages (`Footer.tsx`, `Tour.tsx`) — both sit
  on `--color-bg` (#08080B), so the ≥4.5:1 claim in the statement genuinely holds.
  `text-muted` = 5.88:1, `text-soft` = 12.05:1 — all fine. High-contrast overrides
  (`#F2F2F2`/`#E5E5E5` on elev bg) = 15–17:1.
- **Build:** `npm run build` clean; all 9 routes incl. `/accessibility` prerender
  static. TypeScript passes.
- **Runtime:** started the production server, confirmed skip link (`href="#main-content"`),
  focusable main, widget button (`aria-expanded="false"`), and the `/accessibility`
  page ("Accessibility Statement") all render.
- **CSS override specificity:** `html[data-a11y-contrast="high"]` (0,1,1) correctly
  beats `:root` (0,1,0) — high-contrast tokens actually apply.
- **Widget SSR/hydration:** prefs read from `localStorage` only inside `useEffect`,
  wrapped in try/catch — SSR-safe, no hydration mismatch, degrades gracefully in
  private mode. Escape closes the panel; `aria-pressed`/`aria-expanded`/`aria-label`
  present; keyboard-operable `<button>`s throughout.
- **CSS var references** used by the widget (`--color-bg-elev`, `--color-border`,
  `--color-border-strong`) all exist. No dead references.
- **Security:** static marketing site, no forms/inputs, no `dangerouslySetInnerHTML`
  in the new code, no user-controlled data. `JSON.parse` of storage is guarded.
  Nothing to exploit. Confirms T267's anti-spam (N/A) and privacy (already compliant)
  audit conclusions.
- **eslint `react-hooks/set-state-in-effect`** on the widget is a pre-existing,
  established SSR-hydration pattern (identical shape already in `lib/i18n.tsx`);
  it does not fail `next build`. Left as-is for consistency — churning it would be
  net-negative and SSR-unsafe alternatives (lazy `useState` reading localStorage)
  would crash on the server.

## Minor observations (not bugs — left unchanged per minimal-impact principle)
- `AccessibilityWidget` links to `/accessibility` via a plain `<a>` instead of
  `next/link` → full reload instead of client nav. Functional, just slightly slower.
- `panelRef` is assigned but not used for a click-outside handler; panel closes via
  the toggle button or Escape only. Acceptable for a non-modal dialog.
- Brief FOUC possible if a returning visitor set large-text/high-contrast (prefs
  apply post-mount). Standard tradeoff for SSR + localStorage; matches the site's
  existing i18n behavior. An inline head-script could eliminate it but is out of scope.
